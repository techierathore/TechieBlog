DbUp migrations that never bite back

Ravi Rathore · Senior .NET Architect
featured image · dbup-migrations-hero.webp · 1200×600

Schema migrations are the part of a database-first workflow everyone claims to have solved and almost nobody trusts. After running DbUp in production on three products — including this blog — here is the small set of rules that keeps journal tables boring and deploy nights short.

Rule 1: scripts are immutable, forever

The moment a script has run anywhere outside your machine, it is history — literally. Never edit 0007-add-series-table.sql; write 0012-alter-series-add-sort.sql instead. DbUp's checksum journal will thank you, and so will the teammate who bootstraps a fresh database next quarter.

Rule 2: functions are re-runnable, tables are not

Split your scripts into two folders: run-once DDL and always-run CREATE OR REPLACE FUNCTION definitions. TechieBlog registers the second folder with NullJournal, so every deploy refreshes every PostgreSQL function — the data layer Dapper calls is always the one in source control.

If a script cannot be run twice, it must be run exactly once — and the journal is the only arbiter of "once".

Rule 3: migrate at startup, fail the boot

The host runs DbUp before serving a single request. A failed migration is a failed deployment — loud, early, and rolled back before users notice. Silent drift between app version and schema version is the bug you find at 2 a.m.; this rule deletes that entire category.
