## Goal

Deliver TechieBlog — a production-ready, Blazor-native blogging engine on .NET 10 LTS, distributed as
a clone-and-own template — with a complete authoring, reading and engagement feature set, CSS-variable
theming, a resume/portfolio surface for the site owner, and the operational hardening (tests, CI,
health checks, analytics, newsletter delivery) still outstanding. Traces to `docs/TechieBlog-BRD.md` §1.

**Phase map** (carried from the migrated plan): **1** Foundation & UI scaffolding · **2** Authentication
& user management · **3** Content management core · **4** Engagement & social · **5** Media,
subscribers & analytics · **6** SEO, theming & production polish · **7** Bug fixes & polish ·
**8** Resume, image management & multi-author profiles · **9** UI re-platform (TrBlazeUI) &
portfolio home *(added 2026-08-06)* · **10** BlogApp desktop admin *(added 2026-08-06)*.

- **REQ-UI-056** — **IMPLEMENTED (2026-08-07)** — Captcha widget on every public write surface (BRD-99): challenge image, reload button and answer input, on the comment form, the rating step and the subscribe form. The image is stroke geometry, not text — see REQ-FN-049 for the 2026-08-07 fix that removed the readable answer from the payload. *Mockups:* `02-post-view.html`, `42-newsletter-archive.html`.
  - *Acceptance:* a wrong answer blocks submission with an inline error and issues a fresh challenge; the answer is never present in the page source; the control is keyboard reachable and labelled for screen readers.
  - *Files:* `source/BlogUI/Components/CaptchaWidget.razor` (new). No backend file was touched — the widget consumes the pre-existing, unit-tested `ICaptchaService` / `CaptchaSvc`.
  - *Public contract* (so other clusters can mount it): `<CaptchaWidget @ref="captcha" data-testid="captcha-widget" />` with `Task<bool> ValidateAsync()`, `void Reset()`, `string ChallengeToken`, plus `string Answer`, `bool HasAnswer` and `void ShowError(string)`. Parameters: `LabelText`, `HintText`, `Class`, and `CaptureUnmatchedValues`.
  - *Design notes for the verifier:*
    - **A challenge is SINGLE USE.** `CommentSvc` and `RatingSvc` validate the captcha themselves, so those two callers pass `ChallengeToken` + `Answer` straight through and must NEVER call `ValidateAsync()` — that would burn the challenge before the service could see it. `ValidateAsync()` exists for a surface whose service does not validate (the newsletter subscribe form: `NewsletterSvc`/`SubscriberSvc` contain no captcha step).
    - The challenge is issued from `OnAfterRenderAsync(firstRender)`, never `OnInitialized`. Under the app's global `InteractiveServer` render mode the init pass also runs during the static prerender, which would put a live challenge into the served HTML and burn a cache entry for a visitor who never connects. This is what makes the served page source challenge-free.
    - The SVG is rendered as a base64 `data:image/svg+xml` URI on an `<img>`, not inlined. `CaptchaSvgRenderer` emits the code as SVG `<text>` nodes, so inlining it would put the five characters into the DOM as readable text; encoding keeps them out of the document, out of `textContent` and out of a `grep` of the page.
    - Because a rejecting service has already consumed the challenge, `ShowError(message)` both surfaces the message and issues a NEW image — re-showing the old one would always fail with "expired".
    - **Known residual risk (backend, not this widget):** the glyphs still exist inside the encoded SVG payload, so a client that deliberately base64-decodes the `src` and parses the SVG can read the answer. That is inherent to `CaptchaSvgRenderer`'s text-based SVG and would need a rasterised image or a server-streamed image endpoint to close. The smoke harness uses exactly that decode to drive the "correct answer" path.
  - *Verifier hooks:* `captcha-widget`, `captcha-image`, `captcha-image-placeholder`, `captcha-reload`, `captcha-answer`, `captcha-hint`, `captcha-error`.

- **REQ-NFR-001** — **PARTIAL (2026-08-07)** — Public pages load in under 2 s on broadband and the app serves ≥ 100 concurrent users (BRD-78).
  - **Page load < 2 s — MET.** Real navigation timings against the running app, 12 page/viewport combinations: FCP **72–428 ms**, load event **53–353 ms**, TTFB 6–255 ms. Slowest single figure (resume @1280, FCP 428 ms) is ~5× inside budget.
